## 本轮解决的问题

原商城结算服务由普通下单与智能体报价共同使用。审查发现，金额比较通过 `intValue()` 丢弃小数会误判门槛；按单件先四舍五入再乘数量会丢失或多分配优惠尾差。仅在 Python 确认卡上修正展示不能解决订单落库问题，因此本轮在权威 Java 计价服务中修复。

| 场景 | 修复后的结果 |
|---|---|
| 实际金额 99.99 元，满减或优惠券门槛 100 元 | 不满足门槛；三种优惠券适用范围均使用精确比较 |
| 多档满减门槛含小数 | 按精确金额排序，选择实际达到的最高档 |
| 3 件各 1 元，满减 1 元 | 优惠恰好 1.00 元，应付 2.00 元 |
| 3 件各 1 元，优惠券 1 元 | 优惠券抵扣恰好 1.00 元，应付 2.00 元 |
| 3 件各 1 元，100 积分抵扣 1 元 | 积分抵扣恰好 1.00 元，应付 2.00 元 |
| 同一订单叠加活动、优惠券与积分 | 各项优惠精确守恒，任何明细实付均不为负；超过可抵扣金额时拒绝 |
| 限商品或限分类优惠券 | 只在满足范围的商品中分摊 |

买家聊天页的 SSE 增量处理增加当前 run 存在性判断，解决 TypeScript 的可能为空错误。Python 离线框架检查改为只使用显式测试配置，不读取实时环境变量或 `.env`；从其他工作目录执行也不再依赖 `PYTHONPATH`。模块目录中加购和购物车下单的状态描述同步到实际实现。

## 金额分摊与数据兼容

`MoneyAllocation` 将金额转换为整数分，按可抵扣金额比例分配，先取整数部分，再按余数从大到小补齐剩余分。余数相同时使用稳定的输入顺序。活动商品按商品编号、购物车行编号和 SKU 保持确定顺序；同一数据重复报价会得到相同分摊。无效精度、负数或优惠超出容量时直接拒绝，不静默调整优惠总额。

活动满减先得到精确的购物车行优惠 `promotionTotal`；后续优惠券和积分按上一阶段之后的剩余应付金额分摊。`reduceAmount` 保留供原接口展示单件平均优惠，金额计算改用精确行金额。优惠券资格判断也读取活动后的精确行金额。原积分换算、抵扣比例上限与是否允许和优惠券共用的规则保持现有业务定义。

当前 `oms_order_item` 使用单件两位小数金额加购买数量，无法在单行中表达 3 件商品均分 1 元优惠。因此 `CheckoutItem` 只在需要时拆分**新订单明细**：例如优惠 0.34 元的 1 件和优惠 0.33 元的 2 件。每个优惠阶段对已有组最多再拆为两组，无需逐件展开；三个阶段每个原购物车行最多产生 8 组。

无需数据库字段调整或数据迁移，也不改写历史订单。原库存服务按 SKU 汇总明细数量，库存预留、扣减和释放继续按总购买量执行。订单明细拥有各自真实的 `order_item_id`；后续售后与退款必须按该编号及对应实付金额处理，不能仅按 SKU 合并后假设单件金额完全相同。

普通订单详情可能看到同一 SKU 的多行记录，这是当前存储精度下的兼容性影响。本轮保留原详情逐行展示；智能体确认卡在 `OrderCheckout.lines()` 中按来源购物车行重新汇总，仍然是一条选中购物车行对应一条报价行。订单总额、优惠总额、确认卡行应付及明细落库金额使用同一结果。

## 报价与旧确认卡

Java 报价规则更新为 `ORDER_CHECKOUT_CENTS_V2`。内部指纹在原商品、金额、完整地址、电话和购物车行基础上增加具体分摊结果，包括 SKU、数量、各项单件优惠与实付金额。买家确认后仍由原 Java 订单事务重新计算并核对。

## 建议人工体验

1. 用 `member` 登录买家端，在浏览器切换手机尺寸（例如 390px 宽），进入商城咨询。在已有商品卡选择有效规格与数量，准备并确认加购；检查控件、键盘和按钮是否被遮挡。
2. 点击“选择购物车商品并结算”，选择商品，读取地址与优惠；选择有效地址，按可用积分输入整数，再查看确认卡。确认卡应显示所选规格、总数量、优惠与应付金额；准备确认卡阶段不应生成订单。
3. 如需验证点击体验，明确确认一次测试订单后刷新页面，从卡片进入订单详情，核对商品数量和金额；在原商城取消测试订单。再次查看创建操作时仍显示历史创建成功，订单详情应显示交易关闭。无需付款。

上述体验属于剩余交互检查，不阻塞已完成的网关专项；手机软键盘、触摸选择器及长列表滚动仍需在实际使用设备验收。

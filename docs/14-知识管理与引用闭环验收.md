# 知识管理与引用闭环验收

2026-11-11，`knowledge-0.6`，数据库迁移 `0004`。接续 [13](13-运行基础实施与验收.md)，本轮完成知识资料进入系统、后台构建、员工发布、会员检索回答及来源读取的最小闭环。整个项目仍处于演示阶段，S1 和完整业务尚未完成。

## 已运行的链路

员工登录 → 当前权限复核 → 新增资料 → 上传原件或录入文字 → 新建不可变来源版本 → PG/Rabbit 后台解析 → 人工预览和校对 → 阿里云向量化 → Milvus 新集合写入与回读检查 → 员工明确发布 → N05 检索、阿里云重排 → GPT 根据本次资料回答 → N11/N12 再核验来源并原子保存答复和引用 → 买家读取来源。

| 内容 | 保存位置 | 说明 |
|---|---|---|
| PDF、DOCX、TXT、MD 原件 | MinIO 独立私有桶的 `knowledge/` 目录 | 通过员工鉴权读取，无公开原件 URL |
| 直接录入正文、解析文本、切片、版本、发布指针 | PostgreSQL | 权限与当前有效版本的事实来源 |
| 向量及候选内容 | Milvus 独立数据库 | 可由来源重建；候选结果不能自行授予权限 |
| 任务、重试、失败状态、审计、引用关系 | PostgreSQL | Rabbit 负责唤醒，任务提交仍受租约与 fencing 控制 |
| 商品价格、库存、订单等实时业务信息 | 原 Java/MySQL 商城 | 继续经 Java 工具查询，不复制成知识政策 |

本轮没有将 `docs/` 的需求、数据库设计或架构说明自动导入客服知识，也没有创建正式退换货、配送或价格政策。真实验收使用带 `[TEST ONLY]` 标记的合成资料，验收后均已停用；保留历史和证据方便复核。

## 管理入口与权限

管理端：[知识管理](http://127.0.0.1:5100/#/agent/knowledge)。买家端：[商城咨询](http://127.0.0.1:5173/#/pages/agent/chat)。

新增专用角色 `Agent knowledge editor`，向演示 admin 追加，保留既有角色、资源和菜单。角色包括知识读、编辑、发布、附件上传/读取及本人后台任务读/重试。没有基于 admin 用户名的隐式授权。新登录后可见“智能客服 → 知识管理”；已登录后台可能需要重新登录来刷新菜单，服务端权限仍每次实时检查。

管理页面支持标题搜索、资料分页、版本分页、文本录入、文件上传、解析预览、校对保存、后台任务轮询、失败任务重试、发布、启停。编辑权限与发布权限分别控制按钮和接口。更改可见范围或商品/分类范围会撤回当前发布；已发布正文需通过新版本修改。

上传支持不超过 20 MiB 的 PDF、DOCX、UTF-8 TXT/MD；PDF 不超过 200 页，解析正文不超过 50 万字。解析在独立子进程执行，30 秒超时，DOCX 使用受限 ZIP/XML 解码；不执行宏、外链或嵌入内容。扫描 PDF 没有可提取文字会拒绝，当前不提供 OCR。表格、阅读顺序、图片、页眉页脚和修订仍需人工校对。当前尚无完整恶意文件沙箱及进程内存硬隔离验收。

## 发布与检索边界

1. 上传、解析、构建均不自动发布。发布要求索引任务已经成功、版本为 READY、正文与适用范围摘要一致，且技术回读检查通过。
2. 每个构建尝试使用独立 Milvus 集合。过期 worker 即使完成远程写入，也不能把旧结果提交为当前有效索引。
3. 当前 GENERAL 入口只检索“会员可见、全局范围、已启用、当前发布、READY”的资料。员工内部、草稿、退休版本，以及限定商品/分类的资料均不参与通用咨询。后续需接入可信商品/分类上下文后再开放范围检索，不能相信模型或请求任意传入的商品身份。
4. 候选片段回 PG 核验文档、版本、切片和内容 SHA；最多 20 个候选经阿里云重排选取最多 5 个来源。重排分数阈值为 0.35，此值尚未经过正式业务问答集调优。
5. GPT 只能返回实际候选的序号，不能自行生成来源 UUID。没有证据时返回“无法确认”，不将历史回复当作当前政策。
6. 输出前再次校验来源。完整知识答复、来源块、引用记录和增量事件在一个受运行租约保护的 PG 事务中保存，并通过共享锁与发布/停用串行化。资料在该提交前被撤回会阻止本轮输出；已提交的历史回答仍保留，停用不会追溯删除已读内容。
7. 来源读取要求当前会员确实拥有引用它的已完成消息，并再次核验当前发布/可见状态。版本替换、停用或归属不符返回 `410 SOURCE_UNAVAILABLE`；前端提示重新提问获取当前规则。

当前每次检索最多覆盖 32 份有效全局资料，超过则明确报容量错误，避免静默漏查。正文采用父片段/重叠子片段切分，当前按字符切分，来源提供“正文片段”位置，尚未保留精确 PDF 页码/标题层级和版面。每次构建的检查属于**技术索引完整性与自身召回检查**，不是语义准确率、安全性或政策正确性验收。

## 数据与运行增量

迁移 `0004` 给知识版本增加变更说明、解析报告及解析/索引任务关系，并增加消息到知识切片的引用记录表 `ag_kb_citation`。现在有 33 张 `ag_*` 领域表、4 张 LangGraph checkpoint 表。

复用既有 MinIO、PG、Milvus、Rabbit、Redis，未新增中间件容器。API/generation 只接收 Milvus reader 账号；jobs 接收独立数据库内 builder 账号。scheduler 注册知识任务失败回调，处理最后一次尝试崩溃的领域失败状态。所有供应商密钥和底层连接信息保持在忽略的本机秘密配置中。

Python 激活 operation 从 15 个增加到 31 个，契约仍为 116 个。`SourceCitation` 新增必要的 `chunk_id`，使既有来源读取路径可以实际调用；两端类型由契约重新生成。M08、M09、M16 更新为 PARTIAL，其他工作台仍是未激活的工程入口。

## 下一步

先由业务负责人提供、核对并发布首批真实售前 FAQ、配送、退换和保修资料，再建立“问题—标准答案—允许引用版本”的小规模验收集，评估无答案、相似政策、冲突内容、撤回与提示注入场景。当前技术回读不能替代这一步。

工程上接着完成可信商品上下文与范围检索、稳定的标题/页码切分和父片段扩展、版本回滚、过期向量集合与原件清理、完整审计页与索引容量/恢复测试。随后推进人工接待和受确认控制的交易闭环。语音、治理全工作台、交易/售后专项、留存删除与备份恢复仍未完整实施，不应标记为全系统完成。

## 缺陷复现与修正

| 问题 | 修正前实际证据 | 修正行为 |
|---|---|---|
| 扫描等待附件锁后遗漏新提交保护 | 售后准备持附件锁、插入未提交保护引用；清理的READ COMMITTED语句先看到无引用并等待；准备提交后清理仍将附件置DELETING。专用并发测试实际失败，预期READY但得到DELETING | 扫描取得全部附件锁后，用下一条语句批量重读仍有效/受保护引用，再跳过这些附件，不写删除标记或物理删除job。不能把同一旧SQL快照中的NOT EXISTS当作锁后最新事实 |
| 当前策略已到期的图片仍能成为新凭证 | 图片创建2天、原到期90天，策略已缩为1天；原实现只看retention_until，prepare实际成功，反例预期拒绝却未抛错 | 退货准备按编号顺序批量锁READY、归属正确的图片，再用新语句检查LEAST(原期限,创建时间+当前图片期限)，任何一张不合格即整体回滚 |
| 等待附件锁期间策略改变 | 单次带期限谓词的锁查询仍可能使用等待前的策略快照 | 锁后独立语句读取策略；新增真实锁等待反例验证政策缩短后不会创建保护引用或action |
| 多图反序竞争 | 原逐图顺序由请求数组决定 | 统一按附件编号获取锁；确认卡仍保留用户原始凭证数组，不改不可变业务参数 |

源码：`mall-agent/app/application/retention.py`、`mall-agent/app/application/actions.py`。批量锁后引用核对为一条查询，不为每个附件增加一次往返。遇到扫描后新提交引用时，将跳过数量写入执行进度的既有protected_attachments字段；该字段在试算中是已有保护总数，在执行进度中是锁后新发现引用的跳过数，两个时点不能混为同一统计。

## 隔离PG并发与恢复证据

使用mall_agent_architecture_test，单个pytest进程串行运行。新文件`mall-agent/tests/test_retention_races.py`共7个执行用例，包含人工回复先/清理先两个参数场景。

| 场景 | 实际验证 |
|---|---|
| 当前策略已经过期 | prepare拒绝，action及引用都不落库，附件仍READY等待合法清理 |
| 清理等候有效售后保护事务提交 | 通过pg_stat_activity确认真实Lock等待；提交后附件保持READY、保护引用有效、无附件tombstone或删除任务；锁后保护跳过数至少1 |
| prepare等候附件锁期间缩短策略 | 等待真实发生；策略提交、附件锁释放后prepare拒绝，action及保护引用均无写入 |
| 物理删除期间尝试新增凭证 | 附件DELETING使prepare拒绝，不新增引用；外部对象删除不持SQL事务 |
| 对象删除后、写元数据前job租约失效 | 旧job结果不能提交，元数据仍DELETING；租约回收后新任务再次执行幂等删除并写DELETED。此用例对象存储使用明确的内存替身，真实对象回收另见后文 |
| 到期清理与活动生成 | 真实run被中断且旧fence不能追加/完成，不得读取旧记忆；新run使用更高memory_epoch和独立checkpoint_thread_id |
| 延迟旧checkpoint写入后清理 | 使用真实AsyncPostgresSaver写旧/新线程，模拟旧worker在围栏后迟到写入；延迟清理删除旧线程，保留新线程且新run仍能输出 |
| 人工回复先提交、清理等待 | 通过真实会话锁等待证明串行化；到期正文被擦除，新人工消息保留，接待归属不变 |
| 清理先持锁、人工回复等待 | 同样实际等待并完成；新人工回复保留，无旧内容回流或AI自动接回 |

真实图检查点采用FixtureDialogProvider，不调用供应商；没有把检查点持久化验证称为新模型业务验收。物理删除替身测试明确区分外部IO和PG租约，实际私有对象字节使用后文网关验收证明。

# 加购确认与结果核对闭环验收

2026-11-11，运行版本 `cart-0.8`，PostgreSQL 迁移 `0006`。本次完成 ADD_CART 单一业务动作；买家指普通商城账号，没有新增付费会员机制。完整系统仍处于分阶段实施状态。

## 已跑通的链路

买家提出加购需求 → GPT 在 N06 通过只读工具查询 Java 商品和真实 SKU → 页面让买家选择规格与数量 → Java 重新读取商品、价格和库存并保存 5 分钟准备快照 → Python 保存不可变确认卡 → 买家明确点击确认 → Python 提交确认审计、EXECUTING 与单次投递事实 → Java 在 MySQL 事务中加购并保存结果 → 页面显示结果。没有创建订单、支付、扣款或预留库存。

商品查询无匹配时可显示明确标注的当前商品样本，并要求买家核对，不能宣称样本就是原关键词匹配结果。模型没有 confirm、execute 或任意 URL/SQL 工具。数量和规格由买家选择，模型和浏览器都不能提交权威价格。所有准备、确认、取消与结果查询均检查当前买家身份和会话归属。

## 两库职责与恢复

| 位置 | 已保存事实 |
|---|---|
| PostgreSQL ag_action | 操作编号、参数、参数哈希、Java 报价完整快照、过期时间、control_epoch、状态、结果和确认卡消息关联 |
| PostgreSQL ag_audit_log | 准备、取消、实际点击确认时间、参数哈希、控制世代；不保存买家登录令牌 |
| PostgreSQL ag_action_dispatch | 一次执行投递事实、确认审计引用、加密的仅核对凭据、租约与 fencing token、重试时间、核对次数 |
| MySQL oms_agent_quote | 当前 Java 商品/SKU 价格与数量快照、规则版本、参数哈希及有效期 |
| MySQL oms_agent_operation | 与购物车同事务的成功/拒绝结果、原编号、买家、确认审计编号、控制世代和原始确认时间 |
| MySQL oms_agent_cart_guard | 买家级购物车互斥记录，原购物车增删改、规格变更、清空、购物车下单和新桥接共用 |

执行前按原 operation_no 取得排他锁，再锁买家购物车互斥记录、排序后的商品和 SKU，最后修改购物车。确认时重新检查上架、规格归属、数量范围、库存与准备快照；价格/商品状态变化返回明确拒绝，需要重新准备，不能按变化后的内容直接执行。

互斥记录使用 `INSERT ... ON DUPLICATE KEY UPDATE` 直接取得排他锁，避免 `INSERT IGNORE` 的共享锁升级死锁；购物车写与购物车下单采用 READ_COMMITTED，取得互斥锁后读取当前已提交购物车数量，避免等锁前快照造成数量丢失。原接口保留原业务参数和行为，新增事务与共享互斥保护。

若执行响应丢失、API 退出或 Java 事务回滚，系统保留 UNKNOWN / EXECUTING，不把超时宣称为失败。首次确认请求最多调用一次 execute，HTTP 客户端不重试 execute；后台 scheduler 只拿加密凭据核对原编号。

`FINALIZE_IF_ABSENT` 与执行竞争同一 MySQL 操作主键：执行已提交则返回原结果；执行回滚或尚未开始则原子保存 REJECTED / RECOVERY_NOT_EXECUTED。之后迟到的执行只能读到原拒绝，不能加购。核对接口不调用购物车写方法，也不持有买家 Bearer。锁等待或依赖故障保持 UNKNOWN 并有限退避；核对凭据失效进入 MANUAL_REQUIRED，不伪造终态。

仅核对凭据与执行确认凭据使用不同用途、不同密钥，并绑定 action/operation、买家、参数哈希、控制世代、确认审计、原确认时间和有效期。PG 使用独立 Fernet 信封密钥加密核对凭据。桥接签名仍绑定原始 body、固定路径、时间戳和一次性 nonce；Java 日志对 `/agent-bridge/` 仅记录路径、请求编号与耗时，不记录原始请求体、确认凭据或核对凭据。

转人工、接管或会话控制权变化继续使待确认卡 STALE；已确认操作保持独立结果核对，不伪装成撤回。过期、已取消和终态卡不能再次执行；同一会话存在未知操作时阻止重新准备，以免误解为失败后再次加购。卡片在会话历史中持久化，读历史时重新投影当前操作状态。

## 页面与接口

买家入口：`http://127.0.0.1:5173/#/pages/agent/chat`。选择 SKU 和数量后先点击“查看加购确认卡”，再点击“确认加入购物车”或“取消本次操作”。成功卡显示执行完成时的购物车数量，可跳转原购物车页面；展示的是历史执行时数量，不代表购物车此后不会变化。

本次新增激活 4 个 Python reviewed 操作：prepareAction、getAction、confirmAction、cancelAction，Python 活跃接口合计 52 / 116。Java 新增 quotes、operations、operation 查询与 reconcile；现有商品只读桥接增加真实 SKU 信息。订单创建、取消订单和售后动作仍拒绝，不能因为 Action 枚举包含这些类型就声称已经实现。

后台核对直接消费 `ag_action_dispatch` 持久调度记录，由 scheduler 领取租约；没有把尚未绑定的通用 ACTION_RECONCILE job 声称为已激活。会话结果事件继续使用现有 PG outbox / RabbitMQ / Redis 通知基础。

## 部署与范围

复用现有容器，没有新增容器。MySQL 增量脚本为 `deployment/init/agent-cart.sql`，只新增报价、操作与购物车互斥 3 张表；操作表含确认审计与控制世代增量。PG 0006 仅增加报价快照与消息关联列，仍为 33 张领域表。

首次部署包含新 CartGuard 的 Java 包之前，必须先准备 MySQL 三表，即使暂不开放智能体加购，原购物车接口也要使用互斥表。本机初始化入口 `mall-agent/scripts/prepare_actions.py` 经 SSH 在已有 MySQL 容器内应用增量，再准备独立测试库和库外密钥；不要求开放远程 root 登录。运行开关为 `AGENT_ACTIONS_ENABLED`、`MALL_AGENT_ACTIONS_ENABLED`。密钥只在忽略的运行配置中保存，不进入公开 manifest。

当前购物车展示价使用 SKU 基础价格，确认卡明确提示最终结算优惠以原商城结算页面为准。本轮没有重写或宣称完成统一订单优惠计算器。后续优先完成 Java 统一报价/计价、地址与优惠选择、订单创建和仅核对恢复，然后再开放取消订单与售后。核对凭据续签、MANUAL_REQUIRED 员工处理页、完整业务 outbox、跨会话未知操作治理和长时间故障/容量演练仍待补齐。

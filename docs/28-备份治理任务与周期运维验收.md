| 接口 | 当前行为 |
|---|---|
| GET /mall-agent/v1/admin/backups | 读取预登记备份、认证/恢复状态、策略、执行器心跳和备份告警；UUID游标分页；不返回路径、密钥、秘密配置或原始数据 |

新增deployment/backup-executor.py，由本机管理器以agent-backups受管进程运行。它在原业务暂停期间保持运行，持有数据库会话级唯一执行器锁；失去主锁连接会退出，由管理器恢复。API和普通任务进程只登记/展示任务，不加载SSH或备份密钥处理逻辑，不接受浏览器提供的路径、shell、SQL或恢复目标。

JobHandlers增加固定lane；普通jobs只领取default任务，备份执行器只领取backups任务。BACKUP_VERIFY/RESTORE_VERIFY已激活，ACTION_RECONCILE仍由原dispatch/scheduler路径承接，没有另起一套执行业务逻辑。source/运行迁移仍0010，未增加数据库迁移，受控登记状态保存于ag_setting，任务/审计沿用既有表。

## 维护窗口和任务语义

一致备份仍使用27号的全受管业务暂停、MySQL全局读锁和PG41表SHARE锁。备份预检只允许排除本次有有效租约、owner和fencing的CREATE备份任务自身，其他活动job/run/未决业务或进行中上传仍拒绝；没有用“忽略所有备份任务”绕过排空。

BACKUP_VERIFY的CREATE模式生成实际备份；VERIFY模式只代表归档认证并登记独立恢复任务。RESTORE_VERIFY只有在恢复库、对象、知识、删除覆盖、24笔操作账本/保护关系、不变量和隔离检查成功，并删除本计划隔离资源后，才返回verified=true。前端与任务结果明确区分这两层，认证通过不显示为已恢复。

任务的每次attempt派生固定操作UUID；已有成功封存/验证结果按原编号核验，不能盲目覆盖。脚本超时/取消只停止自己创建的子进程树；备份维护标记不因猜测状态自动删除。恢复失败只尝试清理相同UUID且核验标签的隔离资源；失败/清理错误保留任务和签名结果。旧恢复库的QUEUED/RUNNING后台任务统一置为FAILED/ISOLATED_RESTORE，旧run中断并回收槽位；不重放模型或商城execute。

## 已启用周期策略

最终策略版本3：

| 策略 | 已保存值 |
|---|---|
| 每日一致备份 | 启用，UTC19点，即北京时间次日03点 |
| 每周隔离恢复 | UTC周六19点，即北京时间周日03点；每日备份成功后再排恢复 |
| 日副本 | 保留至少7天 |
| 周副本 | 每ISO周保留一份，保留4周 |
| 删除日志 | 每15分钟生成加密、认证的累计删除/保护日志 |
| 删除保护 | 最新副本、最近已验证副本及排队/运行验证引用的副本不能回收 |

调度按数据库日期和唯一dedupe_key每日一次；晚启动只补当天，不补跑所有错过日期。计划保存版本进入任务，执行前再次检查启用状态和版本。周期CREATE最多有限重试3次；手动及恢复任务首次失败保留，员工按当前权限受限重试。

副本清理只删除签名清单登记的artifact文件，不递归删除目录；保留清单、密钥及过期登记，状态为EXPIRED。领取验证和回收使用记录行锁及活动任务复核协调，避免清理正在验证的备份。周期日志当前有生成和新鲜度检查，日志/密钥及历史演练记录的完整生命周期仍需后续扩展，不能称所有运维资料都已自动清理。
